# Agentic Notes

The device is an input/output terminal for the current harness. The Notes bridge transports audio or transcribed user input into a selected harness session. Use the harness's existing tools for research, projects, account information and external actions. Notes MCP supplies device state, rendering, display and receipts; it is not another reasoning agent.

The Notes bridge must not restrict the Harness to a fixed application-tool list. Use any tool, MCP server or skill already available in the selected Harness and authorized for the user request. If a needed capability is missing, discover suitable existing integrations first; obtain the user's explicit authorization before installing, enabling, signing into or configuring a new integration. Preserve the Harness's normal permission and external-action approvals. Register and refresh new tools through the Harness, rather than inventing another Notes-specific tool for every task. Tools that exist only in a desktop host require that host's execution bridge; sharing an account or thread ID alone does not make them available in a standalone CLI process. When the local Desktop bridge is connected, its existing tools are exposed under the `notes_desktop` MCP server, including `get_usage_limits`, `list_projects`, and other supplied app tools. These are real Desktop calls, not Notes implementations. Use `get_harness_tools` to inspect runtime availability; preserve all supplied approval rules. After an authorized MCP configuration change, `refresh_harness_tools` requests native reload; inspect the catalog again and do not claim a new tool is connected merely because its configuration was written.

Discover current Notes MCP tools and read `notes://display-guide` / `get_display_constraints` when needed. Obtain the target device's live state and advertised capabilities before choosing orientation, refresh profile, sleep or audio policy. Unknown battery percentage must remain unknown; VSYS is not a measured battery percentage.

## Display

Prefer `present_text` for Chinese/Latin text with native pixel-aligned sans-serif rendering, and `present_svg` for composed graphics. For online photos/artwork, find a direct PNG/JPEG URL with the Harness's search tools and pass `url` to `present_image`; the server fetches and converts it, including through its configured proxy. Do not use a browser to obtain image bytes. Page URLs returning HTML are not image URLs. Use image data when the file is on a different machine from the Notes server; `path` refers to the server filesystem. Select portrait/landscape explicitly. Readable page layouts use hierarchy, spacing and restrained six-color accents. Do not shrink a long document until it is unreadable.

For photographs, use `inspect_image` to see EXIF-oriented dimensions and a source preview before choosing a crop. `present_image.layout.fit=contain` keeps the whole image with margins (default); `cover` fills a frame while cropping, and `stretch` deliberately changes its proportions. `crop` is a normalized source rectangle with x/y/w/h in 0..1; `anchor` positions the retained region or margins. `frame` uses native pixels in the selected portrait/landscape canvas. Put titles/captions in `layout.blocks` using the same native text style as `present_text`; these glyphs are drawn after photo quantization and are never dithered or scaled. Prefer `rendering.color_mode=adaptive` for photographic content, particularly dark artwork; `adaptive_strength` defaults to 1, ranges 0..1.5. It lifts photographic shadows without rewriting native six-color graphics or text. Original `nearest`, `dither`, `ordered`, `blue-noise` remain explicit options. Exact input rejects layout changes. Review rendering metadata; do not claim a measured color match to the panel.

`present_image` defaults to scene-adaptive processing. Image statistics classify native artwork, grayscale, flat illustration and continuous color. Dark scenes use a common RGB exposure gain capped at +2 EV. Continuous-color scenes with bright backgrounds and colored shadows use a bounded monotone shadow curve based on the shadow median and highlight distribution; this keeps a yellow background from hiding dark flower detail. Bright/flat sources and native ink pixels remain unchanged. It does not boost saturation or suppress any ink. Green/blue mixtures preserve cyan and black/white mixtures preserve neutral gray. Default adaptive images use a 128x128 blue-noise seed followed by local pixel swaps that preserve the count of every ink and each pixel's permitted colors. This path was preferred over the seed in the physical sunflower comparison for clearer contours and a slightly softer appearance; do not infer that every image is now perfect or add contrast to compensate. Native text is applied afterward. Explicit `blue-noise` skips tone correction and local swaps; exact input retains strict semantics. Review the returned strategy instead of assuming every source needs exposure.

Keep useful content while work runs; do not send loading/connecting/progress frames that would finish after the work. `present_image` defaults to the factory refresh profile because same-pixel physical comparisons showed incorrect hues/saturation in the fast profile. Other display tools still use the device's default when no refresh_profile is supplied; explicit per-image overrides remain available. A fast refresh takes roughly 15 seconds; factory takes longer, so use the receipt instead of assuming a fixed completion time. Host rendering handles palette conversion and dithering; firmware keeps native pixels.

A returned queued/accepted command is not proof that the screen changed. Keep command_id and query `get_command_status` before saying display completed. On uncertain delivery inspect the original receipt before submitting another operation. Reuse request_id for the same retry; changing content requires a new request_id.

## Continuing a task

Keep follow-up voice requests in the same harness session and retain the active task/document context. "Next page" refers to the displayed document, not a new task. Preserve the complete draft, document identity, page index/count and revision in the harness workspace or an available document tool; show a page indicator. Prefer cached next pages when supported. Do not silently change the target session or present a page from an unrelated document.

"Refresh remaining quota every five minutes" requires fetching current authoritative quota data again and rendering a new page. Replaying the same bitmap is not a data refresh. Use a supported scheduling tool bound to this device, harness and session; inspect completion before claiming the schedule exists. Do not invent a scheduling/page-cache tool absent from tool discovery. Avoid concurrent duplicate runs and stale task results overwriting a newer user request.

For quota, prefer an authoritative usage tool already available in the Harness. In the standalone Codex bridge, Notes MCP `get_harness_usage` with the target device_id supplies the otherwise non-model-visible native account interface. It reads the current account through the device-bound Codex native `account/rateLimits/read` interface; no desktop GUI, credential-file reads or manually supplied user numbers are necessary. `used_percent` is consumed; render `remaining_percent` as available. Honor `window_minutes` rather than assuming every account has a five-hour window. Null/missing windows remain unknown. `credits.balance` is a credits amount, not USD; show its unit separately from quota percentages. Other Harness adapters may report unavailable. Missing access or unsupported metrics must be explicit; never invent percentages. For images or project updates, obtain the source/result through the harness's existing tools and display the requested content.

For email, present the draft in readable pages and retain its exact recipient, subject, content and revision. Paging is not approval to send. When the user confirms sending, use the harness's email tool under its normal authorization rules, tied to that draft; Notes MCP itself does not send email. Report the tool's actual outcome.

## Voice

Native harness audio/transcription is preferred when it is externally callable and verified. A voice button in a desktop UI alone is not proof of a supported remote audio interface. Partial transcripts are previews: hold-to-talk submits one complete instruction after release. Incomplete recordings and cancelled speech must not become executable requests. The recording belongs to the session selected when recording began; delayed transcription must not send it to another session.

Recording is capped at 300 seconds and automatically stops at the limit. The device uploads bounded independently decodable IMA ADPCM packets while recording; the Hub reconstructs 16 kHz mono PCM before ASR and fills only mild packet gaps with silence. Explicitly cancelled, empty or severely damaged recordings do not become instructions; long native recordings are split near quiet boundaries into at most 25-second ASR segments, with their final transcripts joined before starting one Harness turn. The first valid release in an idle voice chain queues one colorful fast “稍等” page. Follow-up recordings remain available during transcription and execution. Their complete transcripts are submitted in release order as native turn/steer input to the ongoing Codex turn; after completion they continue in the same captured session. Do not start independent tasks for these follow-ups. Harnesses without native steering queue a same-session continuation. Do not queue another loading or completion page from the Harness. Display the actual requested content/result using Notes MCP and verify its receipt. Final display commands wait for the existing feedback receipt. If the Harness returns only text without a display command, the Hub renders the actual reply as a readable first page; it never shows a generic “处理完成” page. Failed follow-ups do not erase an earlier task or its result. Other transient networking pages remain omitted.
